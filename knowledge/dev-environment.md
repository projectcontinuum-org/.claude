## Gotchas

- **Plain shells pick the wrong tools.** A non-interactive shell (e.g. the agent bash tool) resolves `java` to the
  system JDK 25 (`/usr/bin/java`) and has no Node/Yarn, so `doctor.sh` run there reports `java 25 ok` (it accepts any
  JDK >= 21) and Node/Yarn MISSING. `bash -ic` (= `.claude/factory/scripts/run-with-env.sh <cmd>`) sets `JAVA_HOME` to
  sdkman's `current` (-> `21.0.11-tem`) and has Node 24 / Yarn 1.22: run the doctor and every build that way. This box
  also pins JDK 21 in the gitignored `.claude/factory/local-policy.md`, which the doctor copies into `environment.md`.
- Switch JDKs with SDKMAN (`sdk use java 21.0.11-tem`), not by hand-exporting `JAVA_HOME`/`PATH`: it sets both. (A
  one-line `export JAVA_HOME=... PATH=$JAVA_HOME/bin:$PATH` expands the old `JAVA_HOME` first and can leave
  `/usr/bin/java` first.) `sdk` is a shell function from `sdkman-init.sh`, so a plain shell must source it first.
- **Screenshots/images are never versioned.** Agents write them to `.claude/.screenshots/<task-id>/round-<n>/`
  (ignored by `.claude/.gitignore`; use `SHOT_DIR=<abs path>` for `continuum-system-tests/suites/ui`). Reports cite the path only.

- "Feature not working" after a backend change → the running docker container is probably the old published image
  (this happened with `iteration` in CEL). Rebuild + recreate, then confirm inside the container.
- **Kotlin LS in a dev workbench (verified CONTNM-180, rounds 1-2).** (1) `CONTINUUM_KOTLIN_LS_HOME` was needed in round 1 (bundle `__dirname` made the default dev path one level too high); fixed, a backend without the env var now runs the bundled `.kotlin-ls` (round 2). (2) Use a *seeded* Theia config dir; an unseeded one makes `fwcd.kotlin` ask to download a server (blocks) and then download from GitHub (the fix round says `yarn start` seeds first: NOT VERIFIED). (3) Count Kotlin JVMs by parentage: `ps -eo pid,ppid,rss,etimes,args`, match `org.javacs.kt.MainKt|kotlin-language-server`, walk children of the backend pid (child of the backend = workbench bridge; deeper = the `fwcd.kotlin` extension via the plugin host, only for real `.kt/.kts` files); each is 0.4–0.95 GB RSS. Another agent's instance has its own JVMs whose parent is NOT your backend: ignore them. (4) Theia terminals leave `/bin/bash` children under the backend; ignore them. (5) A development (non-minified) build lets tests reach Monaco/app stores: `window.webpackChunk_continuum_workbench.push([[Symbol('p')],{}, r=>req=r])`, Monaco module `../node_modules/@theia/monaco-editor-core/esm/vs/editor/editor.api.js`; LSP traffic can be read from WebSocket frames (UTF-8 JSON strings). (6) Node output piped through `grep` is block-buffered: write to a file and poll. (7) Monaco popups must be checked for visibility (bounding box inside the viewport), not just presence. (8) A JVM takes `user.home` from the passwd entry, not from `HOME`: to prove a server does not depend on the developer's `~/.gradle`/`~/.m2`, start it with `-Duser.home=<empty dir>` (for the fwcd start script: `JAVA_OPTS="-Duser.home=<empty dir> …"`) as well as `HOME=<empty dir>`. (9) `monaco.editor.tokenize(text, 'kotlin')` loads the `kotlin` language and so wakes the file-editor extension: do not use it when measuring "no second JVM". (10) The bridge forgets a server nobody holds a lease on: to start a test from a cold server, SIGTERM the idle Kotlin JVM under the backend (`kill <pid>`) instead of waiting out the 10 min idle stop. (11) Fault injection in the test browser only (nothing changes on the server): `page.evaluateOnNewDocument` wraps `WebSocket.prototype.send` and keeps the Socket.IO frames of the channel-open message until released (`channel` scenario); a hung server is simulated with `kill -STOP <bridge jvm>` (`hung` scenario: the bridge itself replaces and ends it after ~33 s; the suite still SIGCONT+SIGKILLs the old pid in its cleanup).
- Black-box test runs of the production image: name everything `kotlin-lsp-systest-*` (a round gets its own prefix, e.g. `kotlin-lsp-systest-r2`, and only those objects are removed; never `docker system prune`/`down -v`); `docker exec` as root cannot see another uid's `/proc/<pid>/fd|cwd` (no CAP_SYS_PTRACE), so run process checks as the app's uid; cgroup v2 memory files live under `/sys/fs/cgroup/` inside the container; a `docker run --memory 1g|2g` container emulates the pod limit (not a real pod). A local image tag is not proof of a release: `projectcontinuum/continuum-workbench:0.0.16` was overwritten on 2026-11-28 by a local build of the working tree (Kotlin layers, 5.47 GB against the release's 4.38 GB), and the system tests' compose file pins that tag; compare `docker image inspect` id/created/size and `docker history` before trusting one, and pull the real release by digest (`docker pull <repo>@sha256:...` leaves the tag alone) and tag it under your own name. `node` is not on a plain shell's PATH: run Node tools through `bash -ic`, and pipe through `grep --line-buffered -v "terminal process group\|no job control"` to drop the interactive-shell noise (`cut` block-buffers when writing to a file).
- `ps -eo pid,... --ppid <pid>` is a UNION of the two selections and lists every process: for the children of a pid use `ps -o pid,... --ppid <pid>` or `pgrep -P <pid>`; a Kotlin language server is a child of the backend (bridge) or one level deeper (extension), see the Kotlin LS gotcha.
- Worker image `continuum-feature-base:0.0.10` lacks newer node changes (e.g. Kotlin `flow`) until rebuilt.
- `pkill`/`killall` are blocked: use `pgrep` then `kill <pid>`.
- Workbench `tsconfig.test.json` only compiles `src/common`; specs elsewhere are not run.
- After editing `continuum-core/src/types`, run `npx tsc` in `continuum-core` so `dist/` types update.
- Do not commit product repos unless asked. Co-authored-by trailer rule applies when committing.
- Be honest in reports: state what was not rebuilt/run in a browser.
