# Workbench

Layout (`continuum-workbench/`): `continuum-workbench` (Theia app, run target), `continuum-workbench-thin`,
`continuum-core` (shared TS types `@continuum/core`; has a `dist/` that must be rebuilt with `npx tsc` after editing
`src/types`), `workflow-editor-extension` (main extension), `workflow-builder-extension` (chat agent).

## workflow-editor-extension (`src/`)

- `browser/components/node/` — `BaseNode.tsx` (settings gear, status), `LoopNode.tsx/.css` (container node; header
  responsive: hides condition → max → "LOOP" id → collapse text becomes icon; collapsed width 300; no variable chips
  in the body), `BaseEdge`.
- `browser/components/workflow-viewer/` — `WorkflowViewer.tsx` (React Flow viewer, top-right status icon + `HistoryGauge`
  green ≤50 %, yellow >50 %, red >80 %), `HistoryGauge.tsx`.
- `browser/widgets/workflow-viewer/WorkflowViewerWidget.tsx` — Theia widget; subscribes to live updates
  (`ExecutionService.watch`) and passes status/outputs/history counts down; for stored runs fetches via
  `WorkflowRunsService`.
- `common/` — pure, unit-tested TS (node:test via `tsconfig.test.json`, which only includes `src/common`): loop topology,
  per-depth loop colours/presentation, carried variables, condition query/validation, `HistoryUsage`, `HttpReply`.
  Put testable logic here, keep React files thin.
- `generated/` — OpenAPI clients (never hand-edit).
- Loop visuals: members get a loop badge and the parent's colour; nested loops use distinct subtle colours per depth.
  The condition editor and `common/FlowVariables.ts` mirror do not yet know about `iteration` (open gap).

## Code intelligence (verified 2026-11-27, CONTNM-180 kotlin-lsp requirements)

- Before CONTNM-180 no LSP client/server code existed (the `language-server-extension` workspace and the `fwcd.kotlin` plugin now do). Kotlin highlighting in the dialog is a Monarch registration (`language/MonacoLanguageRegistration.ts`) under the dialog's own Monaco id `continuum-kotlin-script` (since fix round 1; round 2 verified), so the extension's TextMate grammar colours only real `.kt` files (see "Kotlin in the browser").
- Node-dialog script editor = `node-dialog/CodeEditorRenderer.tsx` → `monaco/MonacoEditorWrapper.tsx`: **standalone** `monaco.editor.create` with an in-memory model (not a Theia editor, no file URI), so VS Code extensions in the plugin host never see it. LSP there needs its own bridge (Theia backend `MessagingService` + frontend Monaco client).
- Theia 1.74.1 browser app already has `plugin-ext`/`plugin-ext-vscode` (git extensions only, `theiaPlugins`); no `@theia/vsx-registry`, no `monaco-languageclient`. Production Dockerfile has no JDK.
- Kotlin Script node (`continuum-feature-base` analytics `KotlinScriptNodeModel`): JSR-223 per-row expression with bindings `row` and `flow` (`ScriptFlowVariables`: get/set/all); an LS needs a synthetic prelude declaring them.

## language-server-extension (CONTNM-180, core + browser client landed)

- Backend bridge (`src/node`, generic, verified by specs incl. a real stub server `test/fixtures/echo-language-server.mjs`): `LanguageServerBridgeContribution` (Theia `MessagingService.Contribution`; extension `theiaExtensions.backend`; languages bind to `LanguageServerRegistrations`/`LanguageServerLaunches`) -> `LanguageServerBridge` (route `/services/language-server/:id`, unknown id => channel closed) -> one `LanguageServerHost` per registration. Pitfalls: `BackendApplicationContribution.configure` clashes with `MessagingService.Contribution.configure`, so shutdown is a separate class; a Theia channel message is binary, so JSON-RPC is carried as one string (`writeString`/`readString`). The bridge answers client `initialize` itself (server initialised once, shared), forces advertised sync to Full so document text can be replayed after a restart, remaps request ids per connection, routes diagnostics to the owning connection and answers the server's own requests (`workspace/configuration` etc.). Readiness = a completion request on a probe virtual document (server publishes nothing for clean docs). Memory ceiling = `/proc/<pid>/status` VmRSS vs launch spec `memoryLimitMb` (Linux only). Env: `CONTINUUM_LANGUAGE_SERVER_{IDLE_TIMEOUT_SECONDS,MAX_RESTARTS,WORKSPACES_DIR,WORKSPACE_ROOTS}`. Packaging: `continuum-workbench/scripts/download-kotlin-ls.sh` (pin + sha256, idempotent, `KOTLIN_LS_URL` overrides location only) + Dockerfile stage `kotlin-ls-jre` (temurin 21 jlink, 60 MB) installed under `/opt/continuum/kotlin-ls` with `CONTINUUM_KOTLIN_LS_HOME`/`CONTINUUM_JAVA_HOME`; verified: fwcd server starts on that JRE inside `node:24-slim`. Kotlin language (`src/kotlin`, `src/node/kotlin`, own frontend+backend Theia modules): registration `kotlin-script`; `KotlinScriptPrelude` hoists the user's leading imports above a hidden 2-line header (`import continuum.ScriptFlowVariables`, `fun continuumScript<key>(row: Map<String, Any>, flow: ScriptFlowVariables): Any? = run {`) and a closing `}`; `ContinuumContext.kt` seed file; `KotlinServerLaunch` reads the env vars (default `/opt/continuum/kotlin-ls`, else `.kotlin-ls/`). Pitfall found by running the real server: fwcd ignores documents whose URI is not `file:`, so the bridge shows private-workspace servers virtual docs as `file:` URIs inside the private dir (`VirtualUriTranslator`, applied by wrapping the process factory, both directions). Verified end to end: valid script has no diagnostics, `val x: Int = "a"` gives TYPE_MISMATCH at the right line, `flow.` completes get/set/all, hover shows KDoc. feature-base pins the contract with `KotlinScriptBindingsContractTest` and constants `ROW_BINDING`/`FLOW_BINDING`.

- Browser client (`src/browser`, generic, verified by 135 specs): `LanguageIntelligenceService.attach(model, languageId, registrationId?)` returns a `LanguageSession` (state, statusText, onStateChange) or `undefined` when no registration/monaco (callers keep today's behaviour). One `JsonRpcLspConnection` per registration, shared and closed with the last model. The client sends NO `initialize`: the backend bridge answers it, tracks open documents per wire, replays them to a restarted server, and sends `continuum/serverState` on connect. So the client opens a document once per wire (`onWireChange(true)`), sends full-text `didChange` whenever the wire is open, never reopens on server restarts. Providers are registered per language in Monaco, so each answers only for its own model. Monaco is injected (`MonacoProvider`, structural types in `MonacoTypes.ts`); `TheiaTransportSource` (reconnect with back-off, own retry because Theia's `listen(reconnect)` cannot be cancelled) is the only Theia-coupled piece besides the module. Hosts bind registrations to `LanguageServerRegistrations` and a `MonacoProvider` to `MonacoInstanceProvider`; the service is `LanguageIntelligence`. Pitfall: `vscode-jsonrpc` delivers messages through `setImmediate` one at a time, so specs that use the real connection must wait ~20 ms; the genericity guard also scans spec files (no word `row`/`flow`/`kotlin` even in test strings).

- New workspace `continuum-workbench/language-server-extension` (generic, `src/common/` only so far): registration contract, `PositionMapper`, `DiagnosticFilter`, `LspProtocolPaths` (`/services/language-server/<id>`, `continuum/serverState`, `continuum-script:/<key><ext>`, `isAllowedDocumentUri`). `GenericityGuard.spec.ts` bans language tokens in generic code. Test: `yarn workspace @continuum/language-server-extension test`.
- Spike (verified by running): fwcd/kotlin-language-server 1.3.13 works on a bare 59 MB jlink JRE 21, ~0.8 GB RSS with `-Xmx512m`, first diagnostics ~1.2 s. It needs a root workspace and any shared context file on disk BEFORE start; it publishes no empty diagnostics for clean docs. Script wrapped as `.kt`: hoisted imports + hidden `fun f(row: Map<String, Any>, flow: ScriptFlowVariables): Any? = run {` header. `.kts` mode is experimental/partial. JetBrains kotlin-lsp 271 rejected (needs JBR 25, 1.2 GB, EULA, build-system import). `monaco-languageclient` rejected (needs @codingame monaco build). Details: `.claude/.factory/CONTNM-180/spike-kotlin-ls.md`.

Editor wiring (CONTNM-180): `useLanguageIntelligence` + `LanguageIntelligenceFooter` in workflow-editor-extension; service reaches React via `LanguageIntelligenceStore` (set in `LanguageIntelligenceContribution.onStart`); Monaco is supplied by binding `MonacoInstanceProvider` to the MUI theme store's monaco. Editor-extension specs can only live in `src/common`.
