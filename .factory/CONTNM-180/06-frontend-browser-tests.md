## Round 1

**Verdict.** The Kotlin language support of the **Script node dialog does not work in the shipped build** (workbench built 21:24, served on :3005): the dialog never asks for a language session, so there is no status chip, completion, hover, signature help or diagnostics (AC-4…AC-9 and AC-11 FAIL as shipped). Two independent defects block it, one per half: the editor reads its options from the wrong place (FE-A) and the backend bridge cannot find its server in the local dev layout (BE-A). Behind those two, verified with a clearly labelled in-test-browser workaround, the dialog features work (diagnostics, hover, signature help, completion, two dialogs, save, crash/restart/"unavailable" handling), **but the completion list, hover and signature popups are clipped by the editor box and invisible to a user** (FE-B). The `.kt` file editor (VS Code extension `fwcd.kotlin`) works; `.kts` is only partly usable (BE-D). Opening a Script dialog also starts the extension's own second Kotlin server (≈0.85 GB) even with no `.kt` file open (BE-B).

Finding IDs below (FE-A, FE-B, BE-A…) are this report's own; they are **not** the plan's task IDs (FE-1…, BE-1…). Severity: BLOCKER / HIGH / MEDIUM / LOW. Screenshots (never copied into version control) are in `.claude/.screenshots/CONTNM-180/round-1/` (`$SHOTS` below); file names are `<prefix>-<n>-<label>.png`.

### Answers to the five runtime questions
**Q1 — Does `fwcd.kotlin` activate in Theia's plugin host and give completion/hover/diagnostics for `.kt`/`.kts` (AC-10)? Yes for `.kt`; `.kts` partly.**
- Backend log (plugin host): `Extension: [INFO]   Activating Kotlin Language Server...` then `Creating client at …/continuum-workbench/.kotlin-ls/server/bin/kotlin-language-server` (taken from the seeded `kotlin.languageServer.path`) (24 such activation lines in the :3005 session log; the seeded `kotlin.debugAdapter.enabled=false` is honoured: `Skipping debug adapter registration since 'kotlin.debugAdapter.enabled' is false`).
- `.kt` (`Main.kt`): markers, hover and completion exactly as in the AC-10 row (screenshots `klsp-ship-05/06/07`). The extension's Kotlin server JVM appears **only after a Kotlin model is opened**: `kt-file` run — 0 JVMs with the workspace open and no file, 1 extension JVM (pid 1508370, 835 MB) 3 s after `Main.kt` opened. (But see Q3: the Script dialog counts as a Kotlin model.)
- `.kts` (`tool.kts`): see AC-10 row. Output panel channel `Kotlin` shows `KotlinLSException: Error while analyzing`, `KotlinFrontEndException … /dummy.virtual.kts`, `ClassCastException … LazyPackageDescriptor`; one uncaught `pageerror: Internal error.` was recorded; in an earlier run where `.kts` was opened first there were no markers at all after 180 s (flaky). Screenshots `klsp-ship-08/09/10`, `klsp-fix-09/10/11`.

**Q2 — Does the Script dialog still highlight Kotlin after a `.kt` file was opened (two registrations of the Monaco language `kotlin`)? Yes, identically.**
Token types and colours of the same 4-line sample were compared before and after `Main.kt` was opened (as shipped, clean run `klsp-ship2`, and `[WORKAROUND-OPTIONS]` run `klsp-fix`): identical token scopes (`keyword.hard.kotlin`, `constant.numeric.decimal.kotlin`, `comment.line.double-slash.kotlin`, `string.quoted.double.kotlin`, all `source.kotlin`) and colours (keyword rgb(0,0,255), number rgb(9,134,88), comment rgb(0,128,0), string rgb(163,21,21)). The scopes are **TextMate-style even before any `.kt` file is opened**: as soon as the first `kotlin` model exists (here the dialog's own) Theia loads the extension's grammar (console `Loaded syntax highlighting for kotlin` at dialog-open time) and it wins over the workflow-editor Monarch tokenizer; there is no regression and no visible change, but it also means the Monarch `kotlin` tokenizer is not what highlights the dialog while the extension is installed (AC-9 says "Monarch highlighting"; what the user sees is the TextMate one). Screenshots `klsp-ship2-01-journey-dialog-before-kt`, `klsp-ship2-03-journey-dialog-after-kt`, `klsp-fix-01/03`.

### Failures
All steps use `.cwf` files the suite writes into a temp workspace; the dialog is opened with the node's gear button (`data-testid="node-settings-button-<id>"`).

- **FE-A [BLOCKER, frontend] — the Script dialog never requests language intelligence.** *Steps:* open a `.cwf` with a Kotlin Script node (uiSchema `options: {format:'code', language:'kotlin'}`), open Node Settings. *Expected:* `[data-testid=language-intelligence-footer]` with chip `[data-testid=language-server-status]` (`data-state` starting → ready) within seconds, then completion/hover/diagnostics. *Actual:* highlighted editor, **no footer, no chip, no session** (footers 0, intelligence client `{"connections":0,"hasKotlin":true}`, bridge providers registered 0, no `[language-server]` log line, no bridge JVM). *Cause (read in the served chunk and source, nothing changed):* `workflow-editor-extension/src/browser/components/node-dialog/CodeEditorRenderer.tsx` destructures `options = {}` from the JSON Forms `ControlProps` (lines ~14–25), but JSON Forms puts a control's declared options in `props.uischema.options`; so `options.language` is `undefined` and `<LanguageIntelligenceFooter language={options.language}>` (line ~97) never attaches. Unit specs passed `options` directly in mock props and the frontend review assumed it was populated, so neither saw it. Rewriting that one line in the test browser makes everything work (`[WORKAROUND-OPTIONS]` results). *Pre-existing and related:* `const language = options.language || 'kotlin'` (line ~31, unchanged by this feature) types **every** code editor in the dialog as Kotlin today; once FE-A is fixed Rest/Create Table/Claude editors switch to `freemarker2` / `plaintext` (`freemarker` is not a Monaco language id) / `markdown` — a visible highlighting change versus today (arguably the intended behaviour; flag to the user). *Evidence:* `klsp-ship-01-journey-dialog-before-kt`, `klsp-ship-11…15`, `klsp-ship2-01`.
- **FE-B [HIGH, frontend] — completion list, hover and signature help are clipped by the dialog editor box (invisible).** *Steps:* with a live session type `flow.` / hover `flow.set` / type `flow.set(`. *Expected:* the popup is visible. *Actual:* the editor reports the widget content, the footer says "Kotlin language server ready", but nothing is visible (screenshots show a bare editor line). Measured share of the widget inside the visible editor box: suggest 1 % (1-line script), 5 % (10 lines, cursor at the end), 100 % only with the cursor on line 1 of a ≥20-line editor; hover 0 %; parameter hints 1 %. *Cause:* the container `Box` has `overflow: 'hidden'` and height `min(lineCount,15)×20px` (`CodeEditorRenderer.tsx` ~66–72) and the Monaco instance is not created with `fixedOverflowWidgets`; the widgets render inside the clipped box. Any DOM-only check (items present) passes, so the suite asserts visibility separately. *Direction:* e.g. `fixedOverflowWidgets: true` or a non-clipping container, then re-check visually. *Evidence:* `klsp-fix-12`, `klsp-fix-17`, `klsp-fix-18/19`.
- **BE-A [BLOCKER for local dev runs, backend] — the bridge cannot find the Kotlin server in the dev layout.** *Actual:* backend log `ERROR [language-server] Language server cannot be launched: The Kotlin language server is not installed (/home/maximus/Projects/Project-Continuum/.kotlin-ls/server/bin/kotlin-language-server is missing). Run "yarn download:kotlin-ls"…`; the dialog chip goes `unavailable` immediately and no completion/hover/diagnostics ever arrive (`klsp-be1-02-fallback-unavailable`). *Cause:* `language-server-extension/src/node/kotlin/KotlinServerLaunchSpec.ts` (~line 29) resolves `path.resolve(__dirname,'..','..','..','..','.kotlin-ls')`; in the webpack backend bundle `__dirname` is `…/continuum-workbench/continuum-workbench/lib/backend`, so four `..` land one level above the repo (`yarn download:kotlin-ls` installs into `continuum-workbench/.kotlin-ls`). Same as backend-review BR-1 (static); now confirmed at runtime. The production image sets `CONTINUUM_KOTLIN_LS_HOME` and is unaffected (image run is the backend system tester's scope); with that variable set the bridge works (:3007). The `unavailable` chip gives no reason text; the reason is only in the backend log.
- **BE-B [MEDIUM, needs a decision] — any Monaco model typed `kotlin` starts the extension's second Kotlin JVM.** Opening the Script dialog starts it even with no `.kt` open (Q3: 1 JVM as shipped, 2 ≈1.75 GB once FE-A is fixed); opening a Rest/Create Table/Claude dialog does the same today (AC-18 side effect, via the pre-existing `|| 'kotlin'` fallback); it survives the dialog until the plugin host/browser ends. Confirms the risk in backend-review BR-3 / `03-backend-dev.md`. *Options:* give the dialog's editor model a language id of its own (not `kotlin`) so only real `.kt/.kts` files wake the extension; restrict when the extension activates; or accept and document ≈0.85 GB extra RAM per workbench session (and size pod memory for it).
- **BE-C [MEDIUM, dev workflow] — unseeded dev workbench shows the first-run prompt and blocks.** In a workbench started without `yarn seed:kotlin-settings` the first Kotlin model (a `.kt` file or, with BE-B, any code-editor dialog) raises the "download a language server…" prompt; the extension is blocked until answered and *Ok, continue* downloads server and debug adapter from GitHub (Q4). *Options:* seed from the `start*` scripts, document, or avoid waking the extension (BE-B).
- **BE-D [LOW/MEDIUM, upstream extension/server] — `.kts` is only partly usable.** Whole-file false-positive error `MISSING_SCRIPT_STANDARD_TEMPLATE`, hover shows only that, server exceptions in the Output panel, one uncaught `Internal error.`, sometimes no markers at all. The spike already called `.kts` experimental; either accept as a known limitation or drop `.kts` from the claims.
- **INFO.** (1) Stale completion: after a *wholesale replacement* of previously compiled text, a completion request within the first seconds can return only keywords (`file, field, property, receiver, param, setparam, delegate, import, where, by, get, set`); it self-heals in seconds; the wire traffic was correct (full-text `didChange`, rising versions); not caused by the `.kt` file; the suite appends instead of replacing. (2) The footer/chip texts are "Kotlin language server starting…" / "ready" / "unavailable"; the `unavailable` chip has no reason. (3) Not defects: bridge cwd `/tmp/continuum-language-servers-<uid>/kotlin-script`; each JVM 0.84–0.94 GB RSS (`-Xmx512m`).

### Failures and new findings
- **FE-C [MINOR, needs a decision] — a missing closing `}` or `)` still shows no marker; the FR-3 clamp can never trigger.** *Steps:* in the Script dialog type `if (true) {` ⏎ `println(1)` (also `println(1` and an unclosed 4-line function body). *Expected:* an error marker on the last script line. *Actual:* no marker (`markers: []`; the unclosed function body only gets the warning "Unreachable code" at 4:1), `r2b-01/02/03`; closing the brace → 0 markers (`r2b-04`). *Cause, proven against the real server (scratch JSON-RPC probes in `/tmp`, deleted):* fwcd kotlin-language-server 1.3.13 reports **no syntax (parser) errors at all** — not for the wrapped script and not for plain `.kt` text (missing `}`, `val = 3`, junk at top level, unclosed string or parenthesis, extra `)` / `}` → zero diagnostics); it only reports semantic findings (type mismatch, unused variable, unreachable code). So `showTrailingErrorsOnLastUserLine` has nothing to clamp. The same limit applies to `.kt` files in the file editor (same server; not run in the browser). *Options:* accept and document (the node reports the compile error when it runs), or add a small bracket/quote balance check of our own (frontend or bridge) that produces the marker.
- **FE-D [MINOR, needs a decision] — valid script-level declarations get false error markers.** `object Util { … }` → "Named object 'Util' is a singleton and cannot be local…"; `enum class Color { RED }` → "Modifier 'enum' is not applicable to 'local class'" + "Enum entry 'RED' is uninitialized here"; `interface Greeter` → "'Greeter' is an interface so it cannot be local…"; `typealias Row = …` → "Nested and local type aliases are not supported" (a direct probe also showed `const val` → "Modifier 'const' is not applicable to 'local variable'"). Script-level `class` and `fun` are fine (the only two plain declarations tried in the browser). *Cause:* the wrapper places the script in a function body (`fun continuumScript…(…) = run { … }`), so Kotlin's local-declaration rules apply; this is the second half of review item FR-4 (header placement was fixed, "document the limit or filter those diagnostics" was not done). *Whether the node's own engine (JSR-223 `getEngineByName("kotlin")`) accepts these declarations is NOT VERIFIED* (no platform stack); if it does, they are false red squiggles on valid scripts. `r2e-08…11`, `r2b-10`. *Options:* filter those messages in the registration's diagnostic filter, document the limit, or widen the wrapper after checking the engine.
- **FE-E [LOW] — while a channel open never completes, every retry raises an uncaught `Another channel with the id '/services/language-server/kotlin-script' is already open.` page error.** Seen in the `channel` fault injection at 27.9 s, 39.9 s and 53.9 s of the scenario (12 s and 14 s apart = the 10 s watchdog plus the doubling back-off 2 s and 4 s); none after the held open was answered. Nothing user-visible (chip `unavailable`, editable, Save works, no JVM) and the late answer is adopted. *Likely cause (Theia code path not read here):* the retry calls Theia's `listen` again while the first open is still pending and Theia rejects asynchronously, which the `try/catch` in `ReconnectingTransportSource.attempt` does not see; the review's suggestion "at most one in-flight `listen` per path" is not implemented. *Fix direction:* do not call the opener again while an attempt is outstanding (only re-report), or catch the rejection in `TheiaTransportSource`.
- **BE-D [LOW/MEDIUM, upstream extension/server — unchanged] — `.kts` is only partly usable.** Whole-file false error `MISSING_SCRIPT_STANDARD_TEMPLATE`, hover shows only that, one uncaught `Internal error.`. Round-2 experiment: starting the server directly with `kotlin-script-runtime-2.1.0.jar` (it is in `server/lib`) also added to a scratch Maven repository did **not** remove the error, so it is not a simple repository gap. Decision as in round 1: accept as a known limitation or stop claiming `.kts` support.
- **OBS-J [LOW, observation, not a regression] — JSON editors show no highlighting.** `json` is not a registered language in this workbench's Monaco (94 languages), so the Claude "JSON" editors (`mcpServers`, `outputSchema`) and nothing else are plain text (`r2e-15-rest-j1-dialog.png`); before the feature they were wrongly coloured as Kotlin. I saw no symptom in any run (all passed), and I deliberately did not provoke it (it would have disturbed the other instance).
